# NICs lost after warm reboots: r8125 vs r8169

On the standard (non-Plus) Orange Pi 6, Realtek's `r8125` driver in the sky1 kernel caused both network
ports to disappear after every warm reboot. Mainline `r8169` does not, and it is now the default
(`scripts/02-fetch-patch.sh`, `NIC_DRIVER=r8169`). This page records what we saw, what we tested, and what
is still unknown. All tests ran on one board, firmware `opi6_bios_image_20261019`, kernel 6.18.64 with the
Sky1-Linux patches, booting the sky1 kernel and Armbian 6.18.45 from the same NVMe.

## The hardware

| | |
|---|---|
| NICs | 2x Realtek RTL8125B 2.5 GbE, PCI `10ec:8125` rev 05, chip XID `641` |
| Placement | behind the Sky1 x2/x1 PCIe controllers (firmware "Root Port 2" and "Root Port 3") |
| r8169 firmware | `rtl_nic/rtl8125b-2.fw` from linux-firmware (reported as `rtl8125b-2_0.0.2 07/13/20`) |
| r8125 version | Realtek `9.016.01-NAPI-RSS`, as shipped by Sky1-Linux |

## Symptom

After a warm reboot from a sky1 kernel with `r8125`, the firmware's own PCIe link training fails for both NIC
ports. The serial console shows:

```
Root Port 2: Link Up Fail,Ltssm State:40C80
Root Port 3: Link Up Fail,Ltssm State:40C80
```

The LTSSM field (bits 10-15) is 3, Polling.Compliance. The root port sees the NIC's receivers but never gets
training sequences back. Empty ports read `0x40080` (Detect.Quiet). The firmware then hides those root ports,
so whichever kernel boots next, Armbian included, has no network (`ip -br link` shows only `lo`).

It happened on 9 of 9 warm reboots from sky1 into Armbian. Reboots from Armbian (`r8169`) always trained.
After a failed boot, the next warm reboot trains again, and a power cut of about 30 s also clears it.

## Tests

Each test was a warm reboot from sky1 into Armbian unless stated otherwise. "SysRq-b" is an immediate reboot
over the serial console, which skips every driver's shutdown step.

| # | What we changed | Result | What it ruled out |
|---|---|---|---|
| 0 | `post/0005`: keep PERST# released on reboot (the sky1 PCIe shutdown hook asserted it, and the GPIO keeps that level across the reset) | FAIL 3/3 | PERST# held through the reset |
| 0b | SysRq-b from sky1 (no shutdown hooks run) | FAIL | any shutdown step (sky1 PCIe, r8125, PCI core) |
| 0c | `pcie_aspm=off r8125.aspm=0` | FAIL | ASPM / CLKREQ |
| 1 | Under sky1: unbind r8125, then undo every config-space difference from Armbian (I/O enable, LTR, MaxReadReq, AER status), `pcie_port_pm=off`, SysRq-b | FAIL | the NIC's PCI config space |
| 2 | `post/0007` logged the refclk strap register before and after the driver writes it | unchanged | the PCIe reference clock strap |
| 3 | `post/0008` dumped the RCSU strap and status words at probe and before reboot | straps identical | the controller's RCSU strap settings |
| 4 | `post/0009`: on reboot, take the NIC ports down like the vendor suspend path (PME_Turn_Off, link disable, PERST#, PHY off, clocks off, endpoint power off); NIC ports only, then all ports | FAIL both | sky1 controller / PHY state |
| 5 | `initcall_blacklist=rtl8125_init_module` (r8125 never loads; links still trained by the kernel) | PASS (plain reboot and SysRq-b) | **points at r8125** |
| 6 | `post/0010`: save each EPHY (the chip's own PCIe PHY) register before r8125 first writes it, restore on reboot | FAIL; 0 registers had changed | EPHY settings |
| 7a | r8125 loads but the NICs are never opened (network services masked) | FAIL | anything done at open (`rtl8125_up`); the state is set at probe |
| 8 | sky1 built with mainline `r8169` instead of `r8125` | PASS 5/5 | (fix) |

Test 8 in detail: 3 plain reboots sky1 to Armbian, 1 SysRq-b sky1 to Armbian, and 1 reboot sky1 to sky1. Both
ports trained every time.

An early misreading is worth noting. A sky1 boot whose NIC links never came up rebooted fine, which made the PCIe
controller look guilty. But that boot followed a failed training, and every boot after a failed training trains.
Test 5 settled it.

## Conclusion

`r8125` leaves state in the RTL8125B when it probes. The chip keeps power through a warm reset, and the state
survives PERST#. With it, the firmware's link training cannot get the link past Polling. It is not the EPHY
registers, the PCI config space, ASPM, or anything done at open or shutdown. The remaining candidates are the
MAC MCU patch and the PHY MCU ram code that `r8125` loads into the chip during probe, or other MAC OCP settings
it writes there. A boot option to skip the MCU code (`post/0011`, `r8125.no_mcu=`) was written but not run,
because `r8169` fixed the problem.

## MAC addresses

| | r8125 (sky1, ACPI) | r8169 |
|---|---|---|
| Reads the factory MAC | no: logs `Invalid ether addr 00:00:00:00:00:00` and picks a random one | yes |
| Workaround needed | `.link` files pin the real MACs (`install.sh stage`, from Armbian) | none |
| Side effect | the random, locally administered MAC stays in the chip across a warm reset, so the next kernel can read it as the NIC's own | none |

With `r8169`, `install.sh stage` removes any old pins and `verify` checks none are left. With an `r8125` build
the pins are written as before. `stage` refuses to pin a locally administered MAC.

## r8169 results

- 5 of 5 warm reboots trained both ports (see Tests above).
- Real MACs on both ports, no pins.
- Offloads on: TSO, GSO, scatter-gather, TX/RX checksum.
- 1 Gbit/s link, about 941 Mbit/s each way (line rate) in a 10 s TCP test.
- Clean dmesg.

## Caveats

- **2.5 Gbit/s throughput:** several reports put `r8125` ahead of `r8169` at 2.5 Gbit/s, mostly because
  `r8125` spreads traffic over several CPU cores (RSS) and `r8169` uses one queue. We tested only at 1 Gbit/s,
  where `r8169` reaches line rate.
- **Firmware file:** `r8169` loads `rtl_nic/rtl8125b-2.fw` from the root filesystem. Armbian's linux-firmware
  has it. Without it the driver still works, but logs a warning and runs the PHY on its built-in code.
- **Building with r8125:** `NIC_DRIVER=r8125 scripts/02-fetch-patch.sh`, then build and `install.sh stage` from
  Armbian as before. Expect every warm reboot to lose both ports. A second warm reboot usually recovers, and so
  does a power cut of about 30 s. INSTALL.md describes the smart-plug workaround for that case.

## Open questions

- Which piece of `r8125`'s probe sequence causes it: the MAC MCU patch, the PHY ram code, or another MAC OCP
  write? `post/0011` (`r8125.no_mcu=` bit 0 = MAC patch, bit 1 = PHY ram code) on branch `nic-warm-reboot`
  would answer it without rebuilds.
- Why does `r8169`, which also loads PHY firmware, not trigger it? It may skip the MAC MCU patch for the
  RTL8125B, or load different PHY code.
- What makes the firmware's failure path clear the state, so that the boot after a failed training works? It may
  power-cycle the NIC rails.
- Does the same happen on the Orange Pi 6 Plus, or with other Sky1 boards that use `r8125`?
- `2.5 Gbit/s` throughput of `r8169` on this board is not yet measured.
- The `kernel-7` branch (7.3.5) still uses `r8125` and needs the same change.
